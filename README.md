## 1. Тема и целевая аудитория

**Тема сервиса:** видеостриминговая платформа с персональными рекомендациями, несколькими профилями, офлайн-загрузками и поддержкой высокого качества (HD/4K).

**Основные регионы:** США — 81,44 млн подписчиков, Великобритания — 18,4 млн, Германия — 16,59 млн, Бразилия — 16,59 млн [^100]

**Целевая аудитория:** глобальная аудитория платных подписчиков Netflix.

**Оценочный размер аудитории (MAU):** 301,6 млн платных аккаунтов. [^100]

> В отчётах Netflix «members» — это платные аккаунты; реальное количество индивидуальных зрителей/профилей может быть выше.

### Ключевой функционал MVP

1. Воспроизведение видео
2. Поиск и навигация по каталогу видео
3. Персональная лента рекомендаций (на основе просмотров и профилей).
4. История просмотров, подборки фильмов/сериалов
5. Управление аккаунтом
6. Оффлайн-загрузки и управление скачанными файлами

(Дополнительный функционал включает в себя: лайки/рецензии, live-стримы, торговые интеграция и т.п.)

## 2. Расчет нагрузки

### Продуктовые метрики
- MAU = `301,6 млн` * [^1]
- DAU = 35% * MAU = `105,6 млн` *
- Средняя продолжительность подписки: `4 года` [^5]
- Размер библиотеки: `19 500` **
- Соотношение фильмов и сериалов в библиотеке - `70%` и `30%` соответсвенно [^6]
- 85% потребляемого пользователями в США контента — сериалы [^7]

#### Размер истории просмотров пользователя
- Если соотношение фильмов и сериалов — 70% и 30% соответсвенно, и пользователь в среднем смотрит 63 минуты контента в день [^1], то 44 минуты приходится на сериалы, 19 — на фильмы. Тогда в день пользователь смотрит `44 / 45 = 0,98 серии` и `19 / 90 = 0,21 фильма`. Средняя продолжительность подписки составляет 4 года. То есть пользователь за 4 года посмотрит `(0,98 + 0,21) * 365 * 4 = 1 737 единиц контента`.

\* допущение

\** В 2022 году каталог Netflix состоял из 17 000 позиций [^10]. Рассчитаем примерную скорость роста библиотки. Размер библиотеки в US в 2022 году — 6 473 [^11], в 2024 году — 7 427 [^12]. Следовательно, рост за 2 года составил 14,7%. Тогда на данный момент размер библиотеки равен 17 000 * 1,147 = 19 500.

### Технические метрики

#### Размер хранения

В облачных хранилищах Netflix хранятся 2 типа видео: *оригинальное видео* и *закодированные видео* (для быстрой отдачи контента разного качества). Также есть 2 основных типа контента: фильмы и сериалы.

Соотношение фильмов и сериалов — 70% и 30% соответсвенно. Тогда:
- Количество фильмов: 0,7 * 19 500 = `13 650`.
- Сериалов: 0,3 * 19 500 = `5 850`.
- Средняя продолжительность фильма: `90 мин`.
- Средняя продолжительность серии: `45 мин`.
- Среднее количество серий в сериале - `16` [^14].
- Средняя общая продолжительность сериала: 45 мин * 16 = 720 мин = `12 ч`.

## 4. Локальная балансировка нагрузки

### Балансировка уровней L4 и L7

**L4 — HAProxy / Nginx:**

* Балансировка TCP/UDP соединений
* Используется для статики и видеоконтента
* Алгоритм: Round Robin с весами по производительности серверов

**L7 — Nginx / Envoy:**

* Балансировка HTTP/HTTPS запросов
* Используется для API, поиска, рекомендаций и управления аккаунтами
* Алгоритм: Least Connections с health checks

> SSL Termination выполняется на уровне Ingress подов Kubernetes, снижая нагрузку на сервисные контейнеры. Оркестрация через Kubernetes обеспечивает масштабируемость и надёжность.

### Расчет нагрузки на чтение и запись

- Чтение из таблицы `user`: 105,6 млн / 86 400 = `1 220`, запись — `1` (посчитанный RPS на регистрацию).
- Чтение из таблицы `event` — суммарный RPS на обращение по сегментам для каждого разрешения видео — 57 750 (Low) + 173 250 (Medium) + 115 500 (SD) + 577 500 (HD) + 231 000 (Ultra HD) = `1 115 000`
- Пользователь смотрит контент 63 минуты в день, средняя продолжительность контента — 0,7 * 45 + 0,3 * 90 = 58,5 минут, то есть 63 / 58,5 = `1,08 запросов в день` на пользователя. Тогда при просмотре обращение к таблицам серий и сериалов — 0,7 * 105,6 млн * 1,08 / 86 400 = 924, к таблице фильмов — 0,3 * 105,6 млн * 1,08 / 86 400 = 396. - Чтение из таблицы `thumbnail`: content RPS + первое открытие страницы (105,6 млн / 86 400) - 3 063 + 1 286 + 1 220 = `6 183`

### Требования к консистентности

- Все ключи должны быть уникальными
- Каждому фильму/сериалу соответствует одна запись в content, каждому фильму/эпизоду/трейлеру соответствует одна запись в media; применение каскадного удаления; внешние ключи, связанные с content и медиа, не могут быть пустыми
- При удалении пользователя необходимо каскадно удалять связанные данные

- created_at, updated_at заполяняются автоматически
- Статус notification.status по умолчанию устанавливается в pending

#### NMDB
Отдельно следует более подробно рассмотреть систему хранения медиа контента **NMDB** [^30]. Основными критериями выбора этой архитектуры являются согласованность, долговечность и доступность данных. Рассмотрим принцип ее работы:
- Точкой входа в систему является **NMDB Service**
- Клиент направляет запросы через фреймворк оркестрации **Conductor**, управляющий потоками, связанными с CRUD
- Перед записью данных они проходят проверку в **MDVS** (Media Data Validation Service), который является компонентом сиситемы schema-on-write (проверки корректности схемы данных перед их записью), **MDVS** хранит схемы данных и управляет ими
- Метаданные о медиа хранятся в **Cassandra**, перед ней находится **MDPS** (Media Data Persistence Service), который подтвержает данный по принципу local quorum (подтверждение в пределах ДЦ -> минимизированы задержки, соблюдается принцип read-after-write)
- Индексируются данные для оптимизации поиска в **ElasticSearch**, который управляется **MDAS** (Media Data Analysis Service)
- В объектное хранилище **S3** данные записываются после получения клиентом UUID для генерации уникального URL. Этот URL потом снова возвращается в Cassandra для дополнения записи о медиа файле.

#### ElasticSearch

## 7. Алгоритмы

### Проблематика: collation noise

Современные процессоры устроены таким образом, что гипертреды и физические ядра делят между собой уровни кешей [^32].

![Multi-processor\_multi-core\_multi-thread](assets/images/collation-noise.png)

- красным обозначены гиперпотоки
- тёмно-серым — физические ядра
- светло-серым — CPU-сокеты (NUMA-узлы), использующие общие уровни L2/L3
- зелёным — три уровня кеш-памяти

Из-за совместного использования кешей возникает риск того, что несколько контейнеров окажутся привязаны к одним и тем же ядрам или гипертредам. В этом случае они начинают конкурировать за кеши, что ведёт к появлению **collation noise** — паразитных задержек и деградации производительности.

Ниже показано, как может выглядеть неудачное и корректное распределение потоков между контейнерами (контейнер А использует 4 потока, контейнер B — 2).

![Containers\_placement\_on\_instanse](assets/images/placements.png)

### Классическое управление потоками: CFS

CFS (Completely Fair Scheduler) — это стандартный планировщик Linux [^33].

**Его ключевые особенности:**

* очередь процессов представлена красно-чёрным деревом (*rbtree*),
* порядок определяется значением **vruntime** — временем исполнения с учётом приоритета и нагрузки (учитывается формула вида delta_exec_weighed = delta_exec * (NICE_0_LOAD / curr -> load.weight)),
* каждой задаче запрещено работать на CPU дольше определённого **maximum execution time**, вычисленного относительно «идеального» многопроцессорного окружения.

**Алгоритм работы:**

1. Из дерева выбирается узел с минимальным vruntime (левый элемент).
2. Задача выполняется в течение maximum execution time.
    - Если она завершена — удаляется из дерева.
    - Если нет — процесс приостанавливается, vruntime обновляется, после чего узел снова вставляется в rbtree.
3. Далее цикл повторяется.

#### Недостатки CFS

* планировщик применяет множество эвристик с очень высокой частотой,
* нет защиты от collation noise, что особенно критично для контейнеров, чувствительных к задержкам.

### Predictive CPU Isolation [^34]

#### Основная идея

Необходимо принимать решения о распределении CPU-ресурсов на основе прогнозов и характеристик нагрузки, а не исключительно через механизмы традиционного планировщика.

#### Принципы оптимального размещения

* избегать распределения контейнера между несколькими NUMA-сокетами,
* по возможности не использовать гипертреды, чтобы снизить конкуренцию за кеши L1/L2,
* стремиться равномерно распределять нагрузку на кеш L3 (ориентируясь на аппаратные метрики контейнеров),
* минимизировать частоту перераспределения ресурсов.

### Архитектура решения

**Titus** [^35] — система Netflix, предназначенная для интеллектуальной изоляции CPU и устранения collation noise.

Ключевые элементы:

* базируется на механизмах Linux **cgroups** и сохраняет совместимость с CFS,
* каждому контейнеру выделяется собственный **cpuset**, фиксирующий его привязку к гипертредам/ядрам,
* оптимизационная эвристика не ухудшает предсказуемость производительности,
* решение состоит из:
  * агента на хосте (**titus-isolate**), который управляет cgroups,
  * удалённого **сервиса оптимизации**, решающего задачу распределения ресурсов (MIP-оптимизация).

Агент инициирует запросы на перераспределение при следующих событиях:

* запуск или завершение контейнера,
* необходимость перебалансировки,
* плановое периодическое перераспределение при неудачных предыдущих попытках.

#### Логика работы алгоритма

1. **titus-isolate** отправляет запрос оптимизатору для получения нового варианта размещения.
2. Сервис оптимизации обращается к **GBRT-модели**, предсказывающей загрузку CPU контейнера на 10 минут вперёд.
    * Для прогноза используются:
      * метаданные контейнера (образ, сетевые параметры, выделенная память и т.д.),
      * временные ряды по фактическому использованию CPU за последний час.
3. На основе прогнозов формируется задача **смешанного целочисленного программирования (MIP)**.
4. Так как MIP-задачи являются NP-трудными, оптимизатор работает под временными ограничениями.
5. Если перераспределение невозможно выполнить по триггерному событию, периодическая перебалансировка добавляется в очередь.

## 9. Обеспечение надежности

### Компоненты, обеспечивающие надежность

**Open Connect CDN** обеспечивает доставку контента через кэширующие серверы OCA, размещенные у интернет-провайдеров, что снижает нагрузку на центральные хранилища (AWS S3). В случае сбоя OCA контент автоматически запрашивается из Origin в S3.

**Anycast DNS** использует 4 диапазона IPv4, распределенных по ключевым регионам (США, Европа, Азия, Австралия). Это позволяет автоматически перенаправлять трафик на ближайший рабочий ЦОД при региональных сбоях. 

**Route 53 (DNS)** реализует динамическую балансировку нагрузки через latency-based routing, выбирая оптимальный маршрут на основе задержек.

**Zuul (API Gateway)** выступает единой точкой входа для всех микросервисов, используя кластеры из 100+ экземпляров, распределенных по регионам. Интеграция с Eureka позволяет динамически обновлять список доступных сервисов. Если экземпляр Zuul выходит из строя, трафик автоматически перенаправляется на другие узлы. Асинхронная модель Netty и алгоритм Choice-of-2 для выбора серверов снижают задержки и предотвращают перегрузки.

**Eureka (Service Discovery)** управляет регистрацией и обнаружением микросервисов, используя кластеры с репликацией данных между узлами. Сервисы отправляют heartbeat-запросы каждые 30 секунд, а при отсутствии ответа в течение 90 секунд исключаются из балансировки.

**Titus (оркестрация)** обеспечивает оркестрацию Docker-контейнеров в AWS, используя алгоритм Predictive CPU Isolation на основе GBRT-модели. Это позволяет избегать коллизий кэшей (collation noise) за счет распределения контейнеров по NUMA-узлам. При сбое хоста контейнеры автоматически перезапускаются на других машинах, а Health Checks исключают нерабочие инстансы из пула.

**EVCache** — распределенная in-memory БД, кэширующая частые запросы к PostgreSQL, Cassandra и ElasticSearch. Данные реплицируются между регионами через Kafka и Replication Relay/Proxy, обеспечивая eventual consistency.

**Prometheus** собирает метрики в режиме реального времени (загрузка CPU/памяти, latency микросервисов, ошибки, состояние репликации БД), а **Grafana** визуализирует их на дашбордах. Данные хранятся в S3 для долгосрочного анализа трендов, таких как сезонные пики нагрузки или деградация производительности EVCache.  

**Hystrix** реализует шаблон Circuit Breaker, изолируя сбои в отдельных микросервисах. При падении сервиса Hystrix временно блокирует запросы к нему и возвращает fallback-ответ, предотвращая каскадные отказы. Настройки включают пороги ошибок и время восстановления.

**Chaos Monkey** тестирует отказоустойчивость, случайно останавливая EC2-инстансы, удаляя диски или нарушая сетевые соединения. Результаты тестов фиксируются в Prometheus и используются для доработки архитектуры.

### **Резервирование компонентов**  
| **Компонент** | **Способ резервирования** | **Описание** |
| --- | --- | --- |
| **PostgreSQL** | - Master-slave репликация<br> - Patroni для автоматического failover<br> - Индексация в ElasticSearch через Delta (Kafka Keystone)<br> - EVCache для кэширования частых запросов<br> - Резервное копирование через WAL + логические дампы через pg_dump<br> - PgBouncer для пулинга соединений | **Master-slave репликация**: чтение распределяется между репликами, запись идет только на мастер. **Patroni**: автоматически переключает мастер при сбое. **Индексация через Delta**: данные синхронизируются с ElasticSearch для ускорения поиска и снижения нагрузки на PostgreSQL. **EVCache**: кэширует частые запросы. **WAL + pg_dump**: транзакционные логи и логические дампы сохраняются в S3. **PgBouncer**: управляет пулами соединений, балансируя нагрузку между репликами. |
| **Cassandra** | - Межрегиональная репликация (LOCAL_QUORUM)<br> - EVCache для кэширования<br> - Резервное копирование через snapshot-бэкапы в S3 + incremental backups | **Межрегиональная репликация**: данные копируются в 3+ ЦОД. **LOCAL_QUORUM**: запись подтверждается большинством узлов в локальном кластере. **EVCache**: кэширует метаданные медиа. **Snapshot-бэкапы**: полные копии данных в S3. **Incremental backups**: сохраняются только изменения с момента последнего снапшота. |
| **ElasticSearch** | - Реплики для каждого шарда<br> - Асинхронная репликация в разных ДЦ<br> - Резервное копирование через snapshot-бэкапы в S3 | **Реплики шардов**: каждый шард имеет 2 копии в рамках кластера. **Асинхронная репликация**: индексы копируются в резервные ЦОД с задержкой. **Snapshot-бэкапы**: ежедневные снапшоты хранятся в S3 для восстановления за 5-10 минут. |
| **Tarantool (In-memory)** | - Master-master репликация<br> - EVCache для кэширования | **Master-master репликация**: запись возможна в любой узел, данные синхронизируются между всеми инстансами, полусинхронная репликая гарантирует доступность **EVCache**: кэширует сессии пользователей и токены аутентификации. |
| **S3** | - Multi-AZ + версионирование объектов | **Multi-AZ**: данные автоматически реплицируются в 3+ зонах доступности AWS. **Версионирование**: сохраняются все версии объектов (например, изменения медиафайлов). |
| **Микросервисы**<br> (ex: NMDB) | - Кластеризация, health checks, autoscaling через Kubernetes (Titus)<br> - EVCache для кэширования<br> - Circuit Breaker через Hystrix | **Кластеризация**: сервисы развертываются в 3+ экземплярах. **Health Checks**: Eureka проверяет доступность каждые 30 сек. **Autoscaling**: кластер расширяется при пиковой нагрузке. **EVCache**: кэширует UUID медиафайлов и URL. **Hystrix**: блокирует запросы к упавшим сервисам на 30 сек. |
| **Apache Kafka** | - Репликация партиций (min.insync.replicas=2)<br>- MirrorMaker 2.0 для межрегиональной синхронизации | **Репликация партиций**: каждое сообщение копируется на 3 брокера. **MirrorMaker 2.0**: данные синхронизируются между регионами с задержкой <1 сек. |
| **Hadoop** | - Резервные кластеры в Amazon EMR<br> - Autoscaling на базе Amazon EMR | **Резервные кластеры**: готовые конфигурации для быстрого запуска при сбое. **Autoscaling**: добавляются узлы при пиковой нагрузке. |

## 10. Схема проекта
![Netflix Scheme](assets/images/scheme.png)

[Netflix Scheme](https://www.figma.com/board/g9huYYm50dCZG8uY6Dvuop/Untitled?node-id=0-1&t=IkS2OEil3lM7aeo3-1) 

### Пояснение к схеме

#### Open Connect

* собственная CDN-сеть Netflix, размещённая у интернет-провайдеров;
* хранит предзакэшированные видеофайлы;
* снижает нагрузку на внешние каналы и уменьшает задержки;
* позволяет доставлять видео напрямую от ближайшего CDN-узла.

#### AWS Elastic Load Balancer

* входная точка для клиентского трафика;
* распределяет запросы по сервисам Netflix;
* передаёт запросы в `Zuul`.

#### Zuul 2

**API Gateway** (L7-прокси), выполняющий:

* авторизацию и предобработку запросов (Inbound Filters);
* маршрутизацию запросов к микросервисам;
* обработку ответов (Outbound Filters);
* динамическое определение конечных точек через `Eureka Service Discovery`.

#### Eureka Service Discovery

* внутренняя служба поиска сервисов;
* позволяет Zuul’у находить активные микросервисы и их инстансы;
* обеспечивает автоматическое масштабирование и отказоустойчивость.

#### Titus

* собственная PaaS-система Netflix;
* управляет запуском контейнеров с микросервисами;
* обеспечивает автоматическое масштабирование и развёртывание.

#### Chaos Monkey

* инструмент из набора Chaos Engineering;
* случайно «ломает» сервисы и инстансы;
* проверяет устойчивость и способность к самовосстановлению.

### Микросервисы

#### User Service

* хранение и обработка данных пользователя;
* синхронное чтение/запись в `Tarantool` (низкая задержка);
* кэширование горячих данных через `EVCache`.

#### Streaming Service

* отвечает за выдачу клиенту потокового видео;
* получает ссылки на сегменты медиафайлов от `Media Service`;
* взаимодействует с S3 для получения DASH/HLS сегментов.

#### Media Service

Состоит из четырёх сервисов: `NMDB`, `MDVS`, `MDAS`, `MDPS`

* управляет метаданными и путями к медиафайлам;
* координируется через `Conductor` (оркестратор сложных рабочих процессов);
* хранит информацию в `Cassandra DB` и `ElasticSearch`;
* формирует наборы ссылок на сегменты, отдаваемые в `Streaming Service`.

#### Search Service

* обрабатывает поисковые запросы пользователя;
* читает данные из `ElasticSearch`;
* поисковый индекс актуализируется через `Delta`.

#### Content Service

* хранит основную информацию о фильмах, сезонах, эпизодах;
* работает с `PostgreSQL` (master/slave, CQRS);
* передаёт обновления данных в `Kafka` → `Delta Connector` → `Delta`.

#### Recommendation Service

Состоит из двух уровней:

##### 1. Analytics Service

* собирает события просмотров и активности;
* отправляет данные в `Kafka`;
* обрабатывает большие данные в `Apache Spark`;
* использует `Cassandra` как хранилище пользовательских действий.

##### 2. User Experience Service

* формирует персонализированные рекомендации;
* использует агрегированные данные от Analytics;
* отдаёт рекомендации фронтенду и `Search Service` (для ранжирования).

#### Delta / Delta Connector

* `Delta Connector` отслеживает изменения в `PostgreSQL` (Content Service);
* отправляет их в `Kafka`;
* `Delta` объединяет сырые данные с аналитическими данными из `Analytics Service`;
* формирует «обогащённый» индекс;
* пишет обновления в `ElasticSearch` (для поиска и рекомендаций).

#### EVCache

* распределённый высокопроизводительный кэш Netflix;
* используется `User Service`, `Content Service`, `Media Service`, `Search Service`;
* обеспечивает быстрый доступ к горячим данным (сессии, метаданные, профили);
* поддерживает репликацию между регионами.

#### Kafka

Используется по нескольким направлениям:

* потоковая передача событий (view events, аналитика);
* репликация данных для `EVCache`;
* транспорт обновлений для `Delta Connector` и `Delta`;
* коммуникация между сервисами `Recommendation Service`.

### Monitoring Stack

#### Prometheus

* собирает метрики со всех сервисов Netflix.

#### Grafana

* визуализирует метрики и дашборды производительности.
